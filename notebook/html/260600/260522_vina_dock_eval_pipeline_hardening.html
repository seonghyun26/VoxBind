1. TL;DR

A 4-way 10k-test-split A/B (density / noise / baseline / aligned-density) surfaced four interacting bugs in the Vina dock-eval pipeline. All four are now fixed; the test split is fully evaluated (92/92 baseline + 50/50 aligned-density, zero outstanding vina.error entries), and metrics.json now records the actual cause of any future prep failure — no more silent AttributeError chains.

2. Context: the 4-way 10k test A/B

The investigation started while completing the 3-way 10k-test-split A/B for the X-ray density experiment. Four arms had sampled (or partially sampled) the 100-pocket test split:

  • 260518_voxbind_10k_density (misaligned density, 65 pockets)
  • 260518_voxbind_10k_noise (smoothed-Gaussian-noise control, 62 pockets)
  • 260518_voxbind_10k_baseline (no density, 92 pockets)
  • 260519_voxbind_10k_density_aligned (alignment-corrected density, ep138, 50 pockets after the 8 + 42 expansion)

Two metrics.py batches dock­-evaluated the four arms in waves. The first wave landed most targets cleanly. The second wave — an explicit nohup run from a shell where conda activate voxbind wasn’t in effect — produced an alarming pattern: every dock errored instantly (~0.6–0.9 s/target) with the same exception: 

AttributeError: 'PrepProt' object has no attribute 'prot_pqr'

That symptom led us down the failure chain.

3. The failure chain we untangled

VinaDockingTask.run() in TargetDiff’s utils/evaluation/docking_vina.py looks like this: 

prot = PrepProt(self.receptor_path)
if not os.path.exists(protein_pqr):
    prot.addH(protein_pqr)            # also sets self.prot_pqr
if not os.path.exists(protein_pdbqt):
    prot.get_pdbqt(protein_pdbqt)     # reads self.prot_pqr

PrepProt.addH sets self.prot_pqr before shelling out to pdb2pqr30. PrepProt.get_pdbqt reads self.prot_pqr to invoke prepare_receptor4.py. If addH is skipped (because .pqr already exists on disk) but the freshly-created PrepProt object doesn’t have prot_pqr set explicitly, get_pdbqt hits the AttributeError.

So the visible exception is the downstream symptom. The actual chain is:

  1. An earlier prep attempt created the .pqr but silently failed to write the .pdbqt (its subprocess’ stderr was discarded and its return code was ignored).
  2. The next call starts a fresh PrepProt, sees the orphan .pqr, skips addH, never sets prot_pqr, then crashes inside get_pdbqt.

The real root cause is step 1’s silent failure. Tracing it back: 

def get_pdbqt(self, prot_pdbqt):
    prepare_receptor = os.path.join(AutoDockTools.__path__[0], 'Utilities24/prepare_receptor4.py')
    subprocess.Popen(['python3', prepare_receptor, '-r', self.prot_pqr, '-o', prot_pdbqt],
                     stderr=subprocess.DEVNULL, stdout=subprocess.DEVNULL).communicate()

The 'python3' is a bare name. In a shell where /compuworks/anaconda3/bin appears on PATH before /home/shpark/.conda/envs/voxbind/bin, it resolves to the system Anaconda’s python3. That interpreter doesn’t have MolKit on its sys.path, so prepare_receptor4.py immediately raises: 

ModuleNotFoundError: No module named 'MolKit'

Stderr is discarded, return code is unchecked, no .pdbqt is written. The orphan .pqr sits in the cache until the next run, which then hits the AttributeError at step 2.

4. Fix 1 — _heal_path always-prepends

metrics.py already had a _heal_path() helper meant to keep conda binaries reachable from any shell. The old implementation skipped a real fix when the env was already on PATH: 

def _heal_path():
    _bin = str(Path(sys.executable).parent)
    if _bin not in os.environ.get("PATH", "").split(os.pathsep):
        os.environ["PATH"] = _bin + os.pathsep + os.environ.get("PATH", "")

In the failing shell, /home/shpark/.conda/envs/voxbind/bin was on PATH — just not first. The conditional returned early, the function did nothing, and python3 kept resolving to /compuworks/anaconda3/bin/python3.

The fix is to always hoist the conda env to the front of PATH:

def _heal_path():
    _bin = str(Path(sys.executable).parent)
    parts = [p for p in os.environ.get("PATH", "").split(os.pathsep) if p != _bin]
    os.environ["PATH"] = os.pathsep.join([_bin, *parts])

Verified before/after:

BEFORE heal: which python3 -> /compuworks/anaconda3/bin/python3   (no MolKit -> silent fail)
AFTER  heal: which python3 -> /home/shpark/.conda/envs/voxbind/bin/python3   (has MolKit ✓)
subprocess `python3 -c 'import MolKit'`:  rc=0  stdout=MolKit OK

With PATH ordering fixed and the rest of the failure chain resolved (next sections), 81 of 82 newly-evaluated baseline targets dock’d cleanly on the very next run.

5. Fix 2 — Record the cause in metrics.json

Future prep failures shouldn’t require the “reverse-engineer a downstream symptom” detective work this investigation took. _prepare_receptor was rewritten to invoke the prep tools directly (rather than via PrepProt which silences stderr), capture each subprocess’ stdout/stderr to a .prep.log next to the cache, validate the output file actually exists, and raise an informative RuntimeError: 

def _capture(cmd, stage):
    r = subprocess.run(cmd, capture_output=True, text=True)
    log_buf.append(f"=== {stage} (rc={r.returncode}) ===\n"
                   f"$ {' '.join(cmd)}\n"
                   f"--- stdout ---\n{r.stdout}\n"
                   f"--- stderr ---\n{r.stderr}\n")
    return r

def _raise(stage, r):
    prep_log.write_text("\n".join(log_buf))
    err_lines = r.stderr.strip().splitlines()
    informative = [ln for ln in err_lines
                   if ln and not ln.startswith((" ", "\t", "File ", "Traceback"))]
    summary = "; ".join(informative[-4:]) if informative \
        else "\n  ".join(err_lines[-15:])
    raise RuntimeError(f"{stage} failed for {receptor_cached.name} (rc={r.returncode}). {summary}")

compute_target_metrics catches that and writes a top-level receptor_prep field into metrics.json: 

{
  "version": 2,
  "computed_at": "2026-05-21T...",
  "samples": [ ... ],
  "aggregates": { ... },
  "receptor_prep": {
    "ok": false,
    "error": "RuntimeError: pdb2pqr30 failed for ...pocket10.pdb (rc=1). ...; ValueError: Biomolecular structure is incomplete: Found gap in biomolecule structure for atom ATOM 182 HG2 GLU 866 ...",
    "log_hint": ".vina_cache/...pocket10.prep.log"
  }
}

The reader sees the actual root cause in one glance and a pointer to the full subprocess trace. Crucially, the upstream ValueError: Biomolecular structure is incomplete appears in receptor_prep.error — not just the misleading downstream pocket10.pdbqt does not exist that lives in every per-sample vina.error.

6. Fix 3 — Worker-crash resilience

The parallel docking path used ProcessPoolExecutor with as_completed: 

with ProcessPoolExecutor(max_workers=n_workers) as pool:
    futs = {pool.submit(dock_one, m): slot for slot, m in needed}
    for done, fut in enumerate(as_completed(futs), 1):
        _place(futs[fut], fut.result())   # <-- re-raises if a worker died

run_vina_docking already catches Python exceptions inside the worker and returns {"error": ...}, but a hard worker death (segfault, OOM-kill, BrokenProcessPool, signal) bypasses that and fut.result() re-raises. The exception propagated out of compute_target_metrics, the whole target aborted, and the webapp showed only a generic failure with no metrics.json on disk.

The patched loop now records the worker crash as a per-sample error and keeps going:

with ProcessPoolExecutor(max_workers=n_workers) as pool:
    futs = {pool.submit(dock_one, m): slot for slot, m in needed}
    for done, fut in enumerate(as_completed(futs), 1):
        slot = futs[fut]
        try:
            result = fut.result()
        except Exception as e:
            result = {"error": f"worker crashed: {type(e).__name__}: {e}"}
        _place(slot, result)

The crashed sample shows up in metrics.json["samples"][i]["vina"]["error"]; the next dock-eval run treats it as “needs re-dock” via the smart-cache (_has_vina_for_mode returns False for an error dict), so retries are automatic.

7. target_71 deep dive: a multi-chain pocket

After fixes 1–3, 81 of 82 newly-evaluated baseline targets came through cleanly. One target stubbornly kept failing — not with the AttributeError any more, but with a different error that needed its own investigation: target_71 (TIAM1, CrossDocked entry TIAM1_HUMAN_840_931_0__4gvd_A_rec_4nxr_ans_lig_tt_min_0, structure 4gvd).

The downstream error and what was actually wrong

Every sample of target_71 had this in its vina dict: 

RuntimeError: Error: file .../target_71/.vina_cache/...pocket10.pdbqt does not exist.

With the new _prepare_receptor capturing stderr, the real cause now appeared in receptor_prep.error: 

ValueError: Biomolecular structure is incomplete:
  Found gap in biomolecule structure for atom ATOM 182 HG2 GLU 866

pdb2pqr30’s set_reference_distance() step adds polar hydrogens to a residue and then expects to find the next residue in the protein backbone within bonding distance. For atom HG2 on GLU 866 of chain A, the “next” residue in the file is a completely different chain at a completely different position — pdb2pqr30 detects a gap and gives up.

Why the file has two chains

The _pocket10.pdb file (CrossDocked’s 10Å-cut pocket carve) contains residues from two non-contiguous chains:

chainresiduesrangeatomsclosest atom to ligand
A18861–894130— (host protein)
D (renamed from full PDB’s chain C)51–5313.33 Å

The chain renamed to D in the pocket file (= chain C in the full 4gvd PDB) is the partner peptide — the ligand is sandwiched between chain A and this peptide. So the binding site really does span two non-contiguous chains; the pocket extraction was correct to include both.

Attempts that don’t work cleanly

optionmean vina_dockatoms preservedverdict
pdb2pqr30 with --nodebump / --noopt / --whitespace fail — Gap check is in set_reference_distance(), runs before debumping; can’t be bypassed by flags.

Split-prep-merge (per-chain pdb2pqr30, concatenate .pqr) fail — Chain D alone has 31 atoms but 13 are missing heavy-atom side chains (the 10 Å carve clipped them). Exceeds pdb2pqr30’s repair_limit=0.1 threshold → pdb2pqr30 refuses the partial chain.

8. Fix 4 — Multi-chain prep fallback

The clean fix bypasses pdb2pqr30 entirely for this specific failure mode and feeds the multi-chain PDB directly to prepare_receptor4.py, which has no contiguous-biomolecule assumption. prepare_receptor4.py adds hydrogens itself, assigns Gasteiger charges (instead of pdb2pqr30’s AMBER charges), and writes a valid Vina .pdbqt with all atoms of all chains intact.

The patched _prepare_receptor looks like this:

# Step 1: produce .pqr via pdb2pqr30 (AMBER). On multi-chain-gap,
# skip this step and remember to go direct in step 2.
multichain_fallback = False
if not os.path.exists(pqr):
    r = _capture(["pdb2pqr30", "--ff=AMBER", str(receptor_cached), pqr],
                 stage="pdb2pqr30")
    if r.returncode != 0 or not os.path.exists(pqr):
        if "gap in biomolecule" in r.stderr.lower():
            multichain_fallback = True
            log_buf.append("=== multi-chain fallback triggered ===\n")
        else:
            _raise("pdb2pqr30", r)

# Step 2: produce .pdbqt — from .pqr normally, or direct from .pdb on fallback.
if not os.path.exists(pdbqt):
    if multichain_fallback:
        cmd = [sys.executable, prepare_receptor4,
               "-r", str(receptor_cached), "-o", pdbqt,
               "-A", "hydrogens", "-U", "nphs_lps_waters"]
    else:
        cmd = [sys.executable, prepare_receptor4, "-r", pqr, "-o", pdbqt]
    r = _capture(cmd, stage=...)
    if r.returncode != 0 or not os.path.exists(pdbqt):
        _raise(..., r)

if multichain_fallback:
    Path(base + ".multichain_fallback").write_text("...explanation...")

The sentinel file <receptor>.multichain_fallback tells compute_target_metrics to flag the situation in metrics.json: 

"receptor_prep": {
  "ok": true,
  "fallback": "multi_chain_direct_pdbqt",
  "note": "pdb2pqr30 failed with 'gap in biomolecule structure';
           prepare_receptor4.py was run directly on the multi-chain .pdb
           (Gasteiger charges). All atoms preserved; charge model
           differs from the rest of the run (AMBER).",
  "log_hint": ".vina_cache/...pocket10.prep.log"
}

9. Dashboard & webapp surfacing

A failing dock used to be invisible. metrics_status() returned "fresh" for any version-2 metrics.json with mtime ≥ samples.sdf mtime, so an error-only target looked identical to a successful one. The vina_* columns were just NaN — same as “docking wasn’t requested.”

Three additions surface failures explicitly:

Dashboard helpers (notebook/00_dashboard.ipynb, Section 0)

def n_vina_failed(metrics):
    """Number of samples whose vina recorded an error.
    Distinguishes 'docking ran and failed' from 'docking never ran'."""
    agg = (metrics or {}).get("aggregates", {})
    n = agg.get("vina_n_failed")
    if isinstance(n, int):
        return n
    return sum(1 for s in (metrics or {}).get("samples", [])
               if isinstance(s.get("vina"), dict) and "error" in s["vina"])

A new vina_n_failed column joins PER_TARGET_COLS; experiment_aggregate sums it (not averages) so a run-level total is meaningful.

Section 1 overview

The docking column now shows both target-level coverage and sample-level errors:

Baseline includes target_71 with the multi-chain fallback (Gasteiger charges) — receptor_prep.fallback flags this in its metrics.json. Including it shifts the baseline mean from −7.169 (91-target) to −7.142 (92-target). Affects all summary stats by ~0.03 kcal/mol.

Readouts (unchanged by the receptor-prep work)

  • Density vs no-density. All three with-density arms (real, noise, aligned) cluster within 0.13 kcal/mol on Vina dock. Baseline (no density) is ~0.2–0.3 below. The density channel gives a marginal lift over no-density baseline, and density CONTENT (real vs scrambled noise) doesn’t distinguish itself. Same readout the 100ep pilot gave at 1/100th the data scale.
  • The alignment fix is smaller than the 8-pocket pre-print suggested. On 50 pockets, aligned-ep138 (−7.354) is within sample noise of misaligned-ep99 (−7.485). The earlier −8.13 reading on 8 pockets was a lucky-subset artifact.
  • More training helps modestly. Aligned ep81 → ep138 on the same 8 pockets: dock −8.026 → −8.128 (Δ −0.10). Validity already saturated; diminishing returns.

11. Open follow-ups

  1. Charge-model audit for the multi-chain fallback target. target_71’s −4.707 is on Gasteiger charges; the rest of the baseline is on AMBER. The numbers are not strictly comparable. For a publishable A/B we might want to either (a) re-dock every baseline target with Gasteiger as a sensitivity check, or (b) caveat target_71 as “Gasteiger-charged” in any paper-style table.
  2. Sweep the rest of the CrossDocked test split for multi-chain pockets. target_71 is the only known case in the 92-target baseline run, but other (currently un-sampled) pockets might have the same structural quirk. A pre-scan that just counts unique chain IDs per _pocket10.pdb would surface them all in seconds.
  3. Dashboard support for receptor_prep. The Section 0 helpers know about vina_n_failed but not receptor_prep. A target with receptor_prep.fallback != null deserves a visible marker (e.g. a “FALLBACK” badge in the per-target table) so it doesn’t silently mix into AMBER-charged means.
  4. Memory: the “which python3 in nohup” gotcha is now in project_docking_eval.md. Future sessions inherit it. If we ever script another long-running batch outside the activated env, double-check the PATH before launching.
