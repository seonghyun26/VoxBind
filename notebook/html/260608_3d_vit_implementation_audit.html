3D ViT Implementation Audit

Review of VoxBind's 3D ViT density/atomblob pretraining path, density data handling, downstream integration, and likely misalignments.

Date: 2026-06-08 Repo: VoxBind Scope: code review + CPU shape sanity check No source code changed

Executive Verdict

The core 3D ViT tensor path is internally consistent for the intended cubic 64^3 inputs: patch embedding, token flattening, learned positions, transformer blocks, and unpatchifying back to a full-resolution feature map all line up. A small CPU sanity check confirmed exact patchify/unpatchify round-trip behavior and expected forward output shape.

The larger risks are integration and data-contract risks: multi-channel atomblob pretraining checkpoints do not currently match the downstream VoxBind density branch, one finetune script freezes the zero-initialized fusion layer, validation caches can be reused across incompatible density crop versions, and the on-the-fly CCP4 path is not frame-corrected.

Bottom line

Architecture code: mostly shape-correct, but needs guards and stronger locality/mask design.

Data processing: good in the aligned-crop + xray-only configs; unsafe in fallback or stale-cache cases.

Downstream alignment: the biggest issue. Pretraining mode and downstream input mode must be made explicit and enforced.

Findings

Severity Finding Evidence Impact Recommended fix
Major Multi-channel ViT pretraining checkpoints do not drop into the current downstream density branch. Pretraining supports n_in_channels=11/12/13 via input_mode and validates this at startup in voxbind/train_density_vit_mae.py:1119-1125. Downstream VoxBind creates the density branch with only n_dens_in = 1 or 2 in voxbind/models/voxbind.py:98-119. Loading is strict in voxbind/models/__init__.py:71-82. A 12- or 13-channel atomblob+density encoder cannot be loaded into a downstream branch that receives only X-ray density (+ optional gradmag). If forced by adapting weights, the learned first-layer semantics would not match the input. Pick one deployment contract and enforce it:

Option A: current downstream contract: pretrain only density or density+gradmag encoders for VoxBind.density_encoder.
Option B: add a true multi-channel downstream ViT branch that consumes the same [ligand atomblob, pocket atomblob, density, gradmag] layout, or a separate context_encoder path.
Option C: introduce a documented adapter for patch_embed.weight, but treat it as partial transfer rather than drop-in loading.
Critical train_xray.py freezes the zero-initialized fusion layer, making the density branch inert. density_proj is zero-initialized in voxbind/models/voxbind.py:146-150. The finetune script keeps only parameters whose name contains density_encoder trainable in voxbind/train_xray.py:345-355. With density_proj.weight == 0 and frozen, the model output is independent of x_dens. Gradients to the density encoder are also zero because the frozen zero projection blocks the backward path. Train density_proj together with density_encoder, at minimum: 
if "density_encoder" in name or "density_proj" in name:
    param.requires_grad_(True)
else:
    param.requires_grad_(False)
Also log separate gradient norms for density_encoder and density_proj during the first epoch.
Major Validation caches can silently mix incompatible density crop versions. The ViT-MAE cache key includes grid, radii, dataset name, subset, density source, input mode, and gradmag, but not crops_dir, normalize, subset_val_n, or crop-version metadata in voxbind/train_density_vit_mae.py:576-590. The downstream training cache has the same issue in voxbind/train.py:406-410. A v2/v3/v4/v5 density-normalization run can reuse an older cached validation tensor and report metrics on the wrong density distribution. This is especially risky because recent configs compare crop normalizations. Add to cache keys: resolved crops_dir, ccp4_dir, dset.normalize, dset.use_xray, subset_val_n, and a manifest checksum or stats.json hash when present. Store the key inside the cache file and verify it on load.
Major On-the-fly CCP4 loading is not frame-corrected for CrossDocked structures. The dataset can fall back to CCP4 maps when precomputed crops are missing. _crop_density supports a frame transform, but __getitem__ calls it without one in voxbind/dataset/crossdocked_xray.py:565-580. The config comment also notes that fallback crops are unaligned. If a training/evaluation run falls back to raw CCP4 maps, density can be sampled in the deposited crystallographic frame while atoms are in CrossDocked's frame. That creates a true atom-density misalignment. For training, fail fast when use_xray=True and aligned crops_dir is unavailable. For exploratory on-the-fly mode, load and pass the per-structure Kabsch transform produced by preprocessing.
Moderate Real-density pretraining does not enforce xray_available. In the MAE prefetcher, density_source == "xray" directly uses batch["xray_density"] in voxbind/train_density_vit_mae.py:312-317. Missing density is represented by zeros in voxbind/dataset/crossdocked_xray.py:582-588. The intended configs use subset_xray_only: true, which makes this safe. If a config omits that filter, zero crops become valid MAE targets and can pollute pretraining. When density_source=xray, assert batch["xray_available"].all() unless an explicit allow_missing_xray flag is set. Log the availability fraction at dataset construction and per epoch.
Moderate DensityViT.forward lacks explicit input-shape guards. The encoder stores grid_dim, patch_size, and n_in_channels, but forward only applies patch_embed and adds pos_embed in voxbind/models/density_vit.py:192-201. Most wrong shapes will error, but a non-cubic tensor with the same number of tokens could pass the position addition and then be reshaped as an 8x8x8 token cube. That would silently scramble geometry. Add shape checks before patch_embed: 
B, C, D, H, W = density.shape
assert C == self.n_in_channels
assert (D, H, W) == (self.grid_dim, self.grid_dim, self.grid_dim)
Also assert z.shape[1] == self.n_tokens before adding pos_embed.
Moderate Zero masking is ambiguous for density and atomblob inputs. MAE mode creates x_in = x_noisy * (~mask) in voxbind/train_density_vit_mae.py:389-390. Zero is also a natural value: empty atom voxels are zero, and z-scored density has zero as mean density. The model can confuse "masked" with "valid empty/mean" unless it infers the mask from all-channel absence. This is particularly weak for atom-only empty patches. Use a learned patch-level mask token after patch embedding, or append an explicit mask channel during MAE pretraining. The downstream encoder can still remain clean by making this logic local to DensityViTMAE.
Moderate The pure patch decoder can create blocky local features and weak boundary continuity. DensityViT maps each token to c_out * patch_size^3 voxels with one linear projection in voxbind/models/density_vit.py:159-201. The downstream fusion receives this full-resolution map directly. Attention mixes patch tokens globally, but voxel-level detail inside each 8^3 patch is generated independently per token. This can produce patch boundary artifacts or insufficient local inductive bias for density geometry. Add a small post-unpatch local refinement block, for example Conv3d(C/2,C/2,3,pad=1) + SiLU + Conv3d(C/2,C/2,3,pad=1), or test overlapping patch embedding / a UNETR-style decoder. Keep this optional because it changes checkpoint compatibility.
Moderate Learned absolute positional embedding is fixed to one grid/patch layout. The model creates pos_embed of shape (1, n_tokens, dim) in voxbind/models/density_vit.py:144-151. It is fine for the current fixed 64^3, patch=8 setup, but brittle if grid size, patch size, or crop policy changes. It also does not encode useful 3D relative offsets in attention. Add 3D sin-cos initialization or relative position bias. If keeping learned absolute embeddings, implement interpolation for new g_p^3 layouts and validate shape at checkpoint load time.
Moderate Density normalization happens before geometric augmentation, not after. The dataset normalizes, then rotates/translates density in voxbind/dataset/crossdocked_xray.py:557-563 and 573-579. Gradmag is computed after augmentation and z-scored in 597-607. Interpolation and zero padding can shift the final density mean/std. This is probably small, but it means "normalized crop" does not strictly mean normalized after the exact tensor the model consumes. Measure post-augmentation mean/std. If drift is meaningful, add optional post-augmentation normalization for density, or bake the exact same augment-normalize order into precomputed crops and all downstream evaluation.
Minor patch_mlp reconstruction head is very narrow in recent configs. Recent 40M configs use head_hidden_dim: 67 for an input vector of 16 * 8^3 = 8192 features and output of roughly 12 * 8^3 or 13 * 8^3. This saves compute, but the narrow bottleneck may constrain reconstruction gradients and bias the encoder toward low-rank patch summaries. Ablate head_hidden_dim values such as 128, 256, and 512; compare with the conv head and a modality-split head. Track downstream transfer, not only MAE loss.
Minor Training-time sampling in train.py does not pass density to sampling. sample.py handles density correctly, but train.py's sample() calls sample_molecules(...) without density. Generated samples during training are not representative for density-conditioned models, even though train/val forward passes use density. Mirror the density preparation logic from sample.py inside train.py sample(), or route all sampling through one shared helper.

What Looks Correct

  • The ViT reshape helpers are inverse-consistent for cubic grids. Local CPU check: patch roundtrip True.
  • DensityViT produces (B, C_out, G, G, G), matching the CNN density branch interface.
  • The pretraining script has a single _channel_layout() source of truth and checks model.n_in_channels against the assembled input.
  • For aligned-crop configs, atom coordinates and density receive the same rotation and translation, and gradmag is derived after augmentation.
  • Strict encoder loading catches most accidental architecture mismatches instead of silently accepting missing weights.
  • The weighted MAE recipe addresses real sparsity issues with inverse-frequency atom weights, density downweighting, and atom-positive voxel weighting.

Suggested Fix Order

Fix first

1. Train density_proj with density_encoder in train_xray.py.

2. Add downstream config validation so checkpoint input channels, patch size, dim, depth, and heads match the branch being created.

3. Put density crop version/path metadata into all validation cache keys.

4. Fail fast when using raw CCP4 fallback without frame transforms.

Then improve

5. Add DensityViT.forward shape assertions.

6. Replace zero masking with a learned mask token or explicit mask channel for MAE pretraining.

7. Add local post-unpatch refinement and run patch-size/head-width ablations.

8. Log per-channel reconstruction loss, effective loss weights, and density-branch gradient norms.

Final Assessment

The 3D ViT implementation is not obviously broken at the tensor-layout level. The important question is whether the pretraining objective and downstream consumer are training the same contract. Right now, density-only ViT pretraining maps cleanly to the existing VoxBind density branch, but atomblob / atomblob+density / gradmag pretraining variants need a matching downstream branch or they are only valid as representation ablations, not drop-in density encoders.

The highest-value fixes are small: train the zero-initialized fusion projection, make cache keys density-version-aware, assert xray availability, guard ViT shapes, and fail fast on unaligned CCP4 fallback. After those, architecture work should focus on mask-token semantics and local 3D continuity around patch boundaries.
